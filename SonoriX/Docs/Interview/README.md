## 本文的证据标记

- **【代码已见】**：在当前文件中能找到对应逻辑，不代表我实际运行验证过。
- **【配置已见】**：在场景、资产或包配置中找到设置，实际运行仍可能被代码覆盖。
- **【本人待确认】**：开发动机、时间、原始来源、个人决策及验证经历，需要你自己补充。
- **【建议/练习】**：未来学习或改进方向，不能写成已完成经验。

本轮是静态阅读与文档整理，**没有启动 Unity、打包、运行性能采样或执行设备测试，也没有修改游戏代码**。工程原本存在的未提交修改予以保留。文档描述的是这次读取到的版本，后续代码变化时要重新核对。

## 先纠正上一份介绍中的误区

1. 你说明核心来自现有 LiveLogic 框架与 SUS 解析器，AI 参与扩展。应当据实说明，不能据此宣称底层框架和解析器均由你原创。
2. 当前主播放路径是 `FmodSyncedUnityTimer → EventInstance.getTimelinePosition`。没有证据说明它用 `AudioSettings.dspTime` 驱动判定。
3. 音游时间判定通常不需要 Rigidbody 碰撞。`Update` 中读取统一时间基准并处理输入是可行结构；改成 `FixedUpdate` 并不会自动获得音频同步精度。
4. `UniTask`、`UniRx`、`Addressables` 在本工程受检的业务脚本和包清单中未见使用，属于待补知识。
5. “UniTask 任何情况下都零分配”“Update 中一切 new 都必然造成堆分配”都是过度概括；详见 03。
6. 项目中有 Mesh、Shader 和输入代码，不足以证明具备 3D 建模经验、Arduino 固件开发经验或移动端上线经验。
7. 当前 Git 仓库范围还包含旁边的另一个 `SonoriX` 工程；本手册**没有把邻近工程的重构成果混进当前工程**。

## 复习是否真的有效：三个标准

不用 AI 也能画出一颗 Tap 的执行路线；能解释为什么一次物理输入会对应多个候选轨道；能完成一个小需求、预测边界并说明如何验证。达到这些，比背会架构名词更有帮助。
